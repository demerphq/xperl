=head1 NAME

perlrng - Perl random-number providers

=head1 DESCRIPTION

Perl normally uses its built-in pseudorandom number generator. The special
variable C<${^RNG}> lets a program select a different provider for C<rand> and
C<srand>.

The value of C<${^RNG}> is dynamically scoped and can be localized:

    {
        local ${^RNG} = $rng;
        my $value = rand(100);
    }

Leaving the scope restores the previous provider. Localization selects a
different provider; it does not copy, rewind, or otherwise alter the state
stored in either provider object.

=head1 WHY USE A PROVIDER?

Programs often use random numbers without caring which pseudorandom number
generator produces them.  Tests may need a repeatable sequence, simulations
may need a particular algorithm, and an application may need to replace the
default generator with one that has different state or seeding properties.
Those programs should not have to be rewritten merely because their source of
randomness changes.

C<${^RNG}> provides one standard point at which the source of randomness can
be selected.  A program can use ordinary C<rand> and C<srand> calls, while a
caller, test harness, or dynamically scoped part of the program can install a
different provider with C<local>.  The code using randomness therefore does
not need to accept an RNG object in every API, and libraries do not need to
invent separate provider interfaces for their own functions.

This also gives different parts of the Perl ecosystem a common protocol.
Modules such as C<List::Util> and other CPAN distributions should be able to
use the same provider rather than each defining a slightly different way to
inject or replace an RNG.  Existing module-specific APIs may still be useful
for module-specific operations, but they need not be the only way to control
the randomness used by a program.

The provider protocol is deliberately small and flexible.  A pure-Perl
provider can implement the object or code-reference interface directly.  An
XS provider may take additional care to expose the optional fast callback and
avoid Perl method dispatch in the hot C<rand> path.  This keeps the ordinary
case simple while allowing a provider that needs near-built-in performance to
achieve it without every algorithm being compiled into the Perl core.

=head1 WHY ARE THERE SEVERAL RNG METHODS?

The methods exposed by an RNG module do not all represent separate provider
protocols.  They serve different layers and, in some cases, preserve
interfaces that existing modules already use.

The canonical exchange format for the C<${^RNG}> provider protocol is a byte
string.  C<rand_bytes> can preserve all the bits produced by a provider and
does not depend on the size or precision of Perl's native numeric types.  The
optional XS U64 callback is the efficient internal form used by the core when
an XS provider supplies one.

Methods such as C<rand> and C<rand01> are convenience interfaces.  They are
useful when a caller wants a bounded floating-point result, or when an
existing module already expects a zero-to-one RNG method.  C<rand01_callback>
is another compatibility adapter for APIs that expect a code reference.  They
are not the preferred exchange format for the core provider protocol.

In particular, converting a random word to an C<NV> is lossy on ordinary Perl
builds: an IEEE floating-point value normally has fewer significant bits than
a 64-bit random word.  Using a floating-point value as the internal exchange
currency can therefore discard entropy and can introduce quantization or bias
when the consumer converts it again.  The core consequently obtains bytes or
a native 64-bit word and performs the final conversion itself.  The
floating-point convenience methods remain available because compatibility with
existing callers is important, even though they are not used for the core's
internal provider exchange.

=head1 PROVIDER PROTOCOL

An object provider must implement both of these methods:

    $rng->rand_bytes($length)
    $rng->srand($seed)

C<rand_bytes> must return a binary string containing exactly the requested
number of bytes. C<srand> resets the provider's state and returns the provider's
normal seed result.

An undefined provider selects Perl's built-in generator. An object that does
not provide both required methods is rejected when it is assigned to
C<${^RNG}>; it does not silently fall back to the built-in generator.

An unblessed code reference is called with the requested byte count for random
bytes, and with the seed argument for explicit C<srand>. The code reference
must return the required binary string.

When a non-undef value is assigned to C<${^RNG}>, or selected by localization,
Perl validates its kind and, for an object, verifies that both required methods
are available. This validation happens when the selected value changes. The
provider is not repeatedly revalidated by each call to C<rand>.

The only legal values are C<undef>, an object, or an unblessed C<CODE>
reference. Assigning any other scalar value, including through C<local>,
raises an exception immediately.

=head1 XS FAST PATH

An XS provider can avoid Perl method dispatch on every C<rand> call by
implementing this method as an XSUB:

    get_rand_u64_XS_func_addr()

When an object is assigned to C<${^RNG}>, Perl asks the object whether this
method is available. The method is eligible only when the discovered CV is an
XSUB. A Perl subroutine with this name is ignored and the ordinary provider
protocol is used.

The getter takes no arguments other than its invocant. It returns the address
of a callback belonging to the XS provider's implementation. The provider
owns the layout of the object passed to that callback, so the callback can
recover and update the provider's state without copying it through Perl.

If the XSUB is eligible, Perl calls it once for the selected object. It may
return:

=over 4

=item *

C<undef> or zero, meaning that the normal Perl-level path should be used;

=item *

a non-zero integer containing a callback address; or

=item *

an invalid value, which raises an exception.

=back

The callback address uses Perl's established XS pointer-address convention.
The callback has this C signature:

    typedef U64 (*Perl_rng_u64_func)(pTHX_ SV *provider);

When present, C<rand> uses this callback directly and avoids calling the Perl
C<rand_bytes> method or constructing and decoding an eight-byte temporary
buffer. This optimization applies to the core C<rand> path only;
C<rand_bytes> continues to use the ordinary byte-oriented provider protocol.

The callback is cached in interpreter state. Once selected, C<rand> performs
no C<can> lookup, Perl method lookup, Perl method dispatch, or provider-shape
validation for the request. Those operations happen only when C<${^RNG}>
changes or is restored by localization.

The callback is trusted XS code. Perl can validate that the returned value has
the required integer representation, but it cannot prove that an arbitrary
non-zero address points to a function with the correct signature.

=head1 MULTIPLE PROVIDERS

Each provider object owns its own random state. The cached function pointer
belongs only to the provider currently selected by C<${^RNG}>:

    ${^RNG} = $rng1;       # discover and cache rng1's callback
    ${^RNG} = $rng2;       # replace it with rng2's callback

Different objects may use different callback functions, and objects of the
same class may share one callback implementation while retaining independent
state.

=head1 PERFORMANCE AND PROFILING

The following figures are an example of the relative cost of the bundled
providers.  They were measured on 2026-09-07 with the local xperl build
configured with C<-O3>, without C<DEBUGGING>, and without threads.  Each fast
provider measurement performed 10 million C<rand()> calls.  The HMAC_DRBG and
SHA measurements performed 1 million calls because they are substantially more
expensive.  The figures are the mean of three C<perf stat> runs measuring CPU
cycles and retired instructions on one particular machine; they are not
portable throughput guarantees.

=over 4

=item *

The built-in provider used 722,497,060 cycles, or 72.2 cycles per call.

=item *

C<RNG::PCG> used 1,075,015,690 cycles, or 107.5 cycles per call (1.49 times
the built-in path).

=item *

C<RNG::Wyrand> used 1,068,132,447 cycles, or 106.8 cycles per call (1.48
times the built-in path).

=item *

C<RNG::Xoshiro> used 1,016,685,325 cycles, or 101.7 cycles per call (1.41
times the built-in path).

=item *

C<RNG::HMAC_DRBG> used 15,369,067,931 cycles for its one-million-call run,
approximately 213 times the built-in per-call cost.

=item *

C<RNG::SHA> used 3,339,176,537 cycles for its one-million-call run,
approximately 46 times the built-in per-call cost.  This is consistent with
its status as a pure-Perl proof of concept rather than a performance target.

=back

The fast-provider profiles show the expected common cost in C<pp_rand>,
C<call_rand>, numeric conversion, and scalar result handling.  They do not
show repeated C<can> lookups or Perl method dispatch: the XS callback is
discovered when C<${^RNG}> changes and called directly thereafter.  The
provider-specific callback and generator logic account for the additional
work.  The HMAC_DRBG profile is dominated by its SHA-256 compression function,
while the SHA provider's cost is distributed across Perl-level hashing,
scalar, hash, and magic operations.

These measurements describe one optimized, non-threaded build and one call
shape.  They should be repeated on the target platform and with the intended
workload before choosing a provider on performance grounds.  They also say
nothing about statistical quality or cryptographic suitability.

For a short-lived command, startup and provider setup can be more important
than the steady-state cost.  As one practical example, C<dumbbench> measured
the following rounded time per iteration when each process performed
1,000,000 C<rand()> calls.  The benchmark used C<--no-dry-run> because dry-run
subtraction is inappropriate for this short-process workload.  These times
include process startup, module loading, provider construction, and the calls.
The run covered the built-in provider and the three fast XS providers; the
slower SHA and HMAC_DRBG providers were intentionally omitted:

=over 4

=item *

Built-in provider: 17.69 ms.

=item *

C<RNG::PCG>: 26.652 ms; C<RNG::Wyrand>: 27.45 ms.

=item *

C<RNG::Xoshiro>: 26.088 ms.

=back

These are practical short-process measurements, not steady-state provider
throughput figures.  The provider should be selected once and reused when a
program performs many random operations.
