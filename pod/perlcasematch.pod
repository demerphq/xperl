=head1 NAME

perlcasematch - a gentle introduction to experimental case and data-shape
matching

=head1 DESCRIPTION

This document introduces the experimental C<case_match> feature.  It assumes
that you know a little Perl, but it does not assume that you have used
data-shape matching before.

Data-shape matching asks two questions at once: does a value have the shape we
want, and which parts of it should receive names?  It combines structural
matching with destructuring.  We use the shorter term C<data-shape matching>
to distinguish it from regular-expression matching.

Enable the feature with:

    use feature 'case_match';

The feature is experimental, so its syntax and behavior may change.

=head1 THE BASIC IDEA

A C<case> examines one subject and tries its C<match> clauses from top to
bottom.  The first matching clause runs.  Clauses do not fall through.  The
outer case body may contain only direct C<match> clauses; an ordinary
statement
or a nested C<case> is not allowed there.  Each clause's attached block is an
ordinary block and may contain normal statements, loops, and nested cases.

    use feature 'case_match';

    case ($value) {
        match (1) { say "one" }
        match (2) { say "two" }
        match (_) { say "something else" }
    }

The underscore is a wildcard.  It matches any value and does not create a
binding, so it is useful as a final default clause.

If no clause matches, C<case> returns C<undef> in scalar context and an empty
list in list context.  A C<case> expression otherwise returns the value of its
selected clause block, just like another block expression.

The part inside C<match (...)> is a data-shape description.  It uses familiar
punctuation, but it is not an ordinary expression and is not evaluated to
produce a temporary value.  The optional part after C<if> is different: it is
an ordinary expression used as a guard.

=head1 BINDINGS, PINS, AND GUARDS

A scalar name in a data-shape description is an implicit, clause-local
binding.
You do not write a separate C<my> declaration for it:

    case ($person) {
        match ({ name => $name, age => $age } if $age < 18) {
            say "$name is a minor";
        }
        match ({ name => $name, salary => $salary, ... }) {
            say "$name earns $salary";
        }
    }

Bindings are tentative.  The matcher does not commit them while it is still
deciding whether the complete data shape matches.  If a later part fails, the
earlier bindings are discarded.  The names become available only after the
complete shape and its guard, if any, succeed.

An unpinned name is a new binding even if an outer scope has a variable with
the same spelling.  A name listed by C<with>, or prefixed with C<^> in the
data shape, is the exception: it refers to an existing scalar and is checked
instead of filled in.

A guard is an ordinary expression checked after the structural match:

    case ($value) {
        match ([ $number ] if $number > 0) {
            say "positive: $number";
        }
        match (_) { say "not a positive one-element array" }
    }

Guards are unrestricted expressions.  They may have side effects or throw an
exception.  A false guard discards that clause's tentative bindings and allows
the next clause to be tried.  An exception is propagated normally, with the
tentative bindings discarded.

=head1 SCALAR DATA SHAPES

Literal numbers and literal strings are different data-shape kinds:

    case ($value) {
        match (1)   { say "the number one" }
        match ("1") { say "the string one" }
    }

This distinction makes the intended comparison explicit.  An undefined value
can be matched directly:

    case ($value) {
        match (undef) { say "no value" }
        match (_)     { say "some value" }
    }

The boolean data shapes C<true> and C<false> use ordinary truth-value rules.
For example, C<match (true)> matches the number C<1>, while C<match (false)>
matches C<0>.  Use C<match (undef)> when undefined and defined-false values
must be distinguished.  There are no separate C<TRUE> or C<FALSE> data-shape
forms.

=head2 Zero-argument calls

A zero-argument function or method call may supply a value computed by a
subroutine:

    sub current_version { 3 }

    case ($version) {
        match (current_version()) { say "current" }
        match (Version->number()) { say "known version" }
    }

The call is made in scalar context when the clause is tried.  Calls with
arguments are rejected because the left side of C<match> is not general
expression syntax.  Use a guard for ordinary computation or a value that
needs arguments.  Calls may have side effects, so use them only when that is
intentional.

=head2 Value-kind criteria

These criteria describe the kind of the subject rather than its contents:

=over

=item C<RefVal()>

Matches any reference, including an unblessed array or hash reference and a
blessed object.

=item C<ScalarVal()>

Matches any non-reference scalar, including C<undef>, numbers, and strings.

=item C<ObjectVal()>

Matches a blessed reference.  It is narrower than C<RefVal()>: an unblessed
reference matches C<RefVal()> but not C<ObjectVal()>.

=back

Inside a data-shape description these names are criteria, not ordinary calls.
Outside a data-shape description they retain ordinary subroutine semantics,
so a program may define or call a subroutine with one of these names.

Each criterion may take one scalar target.  The target is bound after the type
check succeeds:

    case ($value) {
        match (RefVal($reference)) { use_reference($reference) }
        match (ObjectVal($object)) { use_object($object) }
        match (ScalarVal($scalar)) { use_scalar($scalar) }
    }

The target is a clause-local binding and cannot also be pinned by C<with>.
Using a criterion without an argument performs only the type check.

=head2 Numeric value criteria

Numeric criteria distinguish native numeric values from numeric-looking
strings:

=over

=item C<IntStr()>

Matches an integer value or a string containing an integer.  Surrounding
whitespace and leading-zero padding are accepted.

=item C<FloatStr()>

Matches a floating-point value or a string containing a floating-point number.
Exponent notation, surrounding whitespace, and leading-zero padding are
accepted.

=item C<Num()>

Matches a native integer or floating-point value.  A string is not converted
just to make it fit this criterion.

=item C<NumStr()>

Matches anything accepted by C<IntStr()> or C<FloatStr()>.

=item C<NumEq(EXPR)>

Compares the subject with the literal C<EXPR> using numeric C<==> semantics.
It is matching-only and cannot bind a value.

=back

The string-bearing criteria can bind the original value.  Matching C<"0007">
does not turn the binding into C<7>:

    case ($value) {
        match (IntStr($integer_text)) { use_integer($integer_text) }
        match (FloatStr($float_text)) { use_float($float_text) }
    }

C<Strict(...)> may wrap C<IntStr()>, C<FloatStr()>, or C<NumStr()> when a
canonical spelling is required.  Strict criteria reject surrounding whitespace
and non-canonical leading-zero padding.  C<Strict(Num())> and
C<Strict(NumEq(...))> are compile-time errors.

C<NumEq(EXPR)> uses the usual numeric-conversion rules.  For example,
C<NumEq(0)> matches C<"0000">, C<"0.0">, and C<"0000.0">.  It also matches
C<"A"> as zero and emits the usual numeric warning.  A non-literal argument
or a destructuring target is rejected.

=head1 REFERENCE AND OBJECT SHAPES

A backslash describes a scalar reference shape:

    my $number = 42;
    my $reference = \$number;

    case ($reference) {
        match (\$value) { say "the value is $value" }
    }

C<\\$value> describes one additional scalar-reference layer.  A reference
shape is structural; it does not evaluate the description as a reference
constructor.

C<RefVal($name)> is different from C<\$name>.  The former checks any reference
and binds the outer reference itself.  The latter checks a scalar reference
and
binds the value reached through it.  Array and hash shapes can be nested in
the same way.

=head2 Arrays and hashes

An array shape matches an array reference.  Without an ellipsis, it must have
exactly the listed number of elements:

    match ([ $x, $y ]) { say "point: $x, $y" }

A hash shape lists keys that must be present.  A trailing C<...> permits extra
keys:

    match ({ status => "ok", value => $value, ... }) {
        use_value($value);
    }

For arrays, C<...> may appear at the beginning, at the end, or at both ends:

    match ([ $first, ... ])
    match ([ ..., $last ])
    match ([ ..., "start", $middle, "end", ... ])

The last form searches from the left and binds the first matching subsequence.
Array and hash shapes may be nested.  An ellipsis is allowed only in these
supported open-shape positions.

=head2 Array tail bindings

An array shape can capture its remaining tail with an array binding.  The
binding may contain zero or more elements:

    match ([ 1, 2, @rest ]) { say "the rest is @rest" }

The binding must be the final pattern element.  C<@rest:N> requires at least
C<N> remaining elements while capturing the complete tail:

    match ([ 1, 2, @rest:3 ]) { say "three or more: @rest" }

The current implementation permits one final slurp and minimum values from
0 through 255.  A slurp cannot be combined with an ellipsis or another slurp.
Bindings remain tentative until the complete shape and guard succeed.

=head2 Class-qualified shapes

A blessed reference can be matched by putting its class name before an array,
hash, or reference shape:

    my $point = bless { 'x' => 3, 'y' => 4 }, 'Point';

    case ($point) {
        match (Point { 'x' => $x, 'y' => $y }) {
            say "point: $x,$y";
        }
    }

Hash shapes inspect quoted fields, array shapes inspect positional values, and
scalar-reference shapes can bind their referents.  Native class objects backed
by the class field-map representation are supported.  The class name must
match exactly in this version; inheritance and role matching are not used.
Missing fields do not match.  These shapes inspect the object directly and do
not call constructors, accessors, or arbitrary methods.  Tied and magical
nested values use normal read semantics, and overload is used when the
selected shape requires string, numeric, or boolean conversion.  Captured
references retain their identity.

=head1 REGULAR-EXPRESSION SHAPES

A regular expression can be used as a data shape:

    case ($text) {
        match (/^user: (\w+)$/) {
            say "user is $1";
        }
        match (/^person: (?<person>\w+)$/) {
            say "person is $person";
        }
    }

Numbered captures and the usual named-capture variables remain available in
the clause.  A named capture also creates a clause-local scalar binding.  A
named capture that does not participate is bound to C<undef>.  If a regular
expression uses duplicate named captures, the binding follows the regular
expression engine's named-capture lookup rules; it does not create multiple
bindings with the same name.

The match state is localized to the C<case> block.  When the case ends, the
previous values of C<$1>, C<$2>, C<%+>, C<%->, and related match variables are
restored.

Static regular expressions are compiled once and may be reused while an open
array or hash shape searches for candidates.  Dynamic regular expressions,
including interpolated expressions such as C</thing-$re-thing/>, are rejected
in a data-shape position.  Regex code blocks such as C<(?{ ... })> and
C<(??{ ... })> are also rejected.  These restrictions prevent runtime code or
side effects from being silently discarded.  Put such logic in a guard:

    match (_ if $subject =~ /thing-$re-thing/) { ... }

A regular expression cannot currently be used as a fragment of a larger
concatenated string shape.  Unicode and byte behavior remains the
responsibility of the regular-expression engine.

=head1 CONCATENATED STRING SHAPES

A string shape can combine literal text with unpinned scalar names.  Each
name receives the part of the subject between the surrounding literal or
pinned fragments:

    case ($text) {
        match ("x_" . $middle . "_z") {
            say "middle is $middle";
        }
    }

This matches C<x_middle_z> and binds C<$middle> to C<middle>.  Multiple
captures are allowed when literal or pinned text separates them:

    match ("a" . $first . "b" . $second . "c") {
        say "first=$first second=$second";
    }

Matching proceeds from left to right.  Each capture uses the shortest value
that reaches the next literal or pinned fragment.  Prefix-only and suffix-only
forms such as C<"x" . $suffix> and C<$prefix . "z"> are supported.  Empty
captures are allowed.

Each unpinned capture name may occur only once in a concatenation.  Adjacent
unpinned captures, repeated capture names, and fragments separated only by an
empty literal are rejected because they do not provide an unambiguous
boundary.

Concatenation is the only structural expression currently supported.  Calls
with arguments, arithmetic, and other unsupported expressions are rejected;
they are not silently ignored or treated as ordinary code.  Literal strings
and values with usable overloaded stringification follow normal string and
Unicode/byte behavior.  Concatenation does not perform a separate numeric
conversion.

=head1 NAMING AND PINNING

The subject can be given a case-local name with C<as>:

    case (read_record() as $record) {
        match ({ type => "ok", ... }) { use_record($record) }
    }

The subject is evaluated once.  This does not assign to an outer variable.

A C<with> clause pins existing values.  Each item may be a variable or an
expression followed by C<as> and a scalar name:

    case ($record)
    with (expected_type() as $wanted, $wanted_version) {
        match ({ type => $wanted, version => $wanted_version, ... }) {
            use_record($record);
        }
    }

The C<as> syntax in a case subject or C<with> clause belongs to this feature.
It is distinct from the similarly named syntax in the namespace feature, and
does not require the C<namespaces> feature.

An existing scalar can also be pinned directly with C<^$name>:

    my $wanted = "ok";
    case ($record) {
        match ({ type => ^$wanted, ... }) { use_record($record) }
    }

The value is snapshotted when the surrounding case begins, so all clauses see
the same pinned value even if a guard or clause body later changes the scalar.
Only an existing scalar lexical may follow the caret.  Outside a data-shape
description, the caret keeps its ordinary meaning.

=head1 EXPLICIT SUBJECT CONVERSION

The grammar provides three explicit subject conversions:

    case (ToInteger $value) { ... }
    case (ToFloat   $value) { ... }
    case (ToString  $value) { ... }

The subject is evaluated once and converted before any clause is tested.  An
undefined value remains undefined, and references pass through unchanged.

=head1 A COMPLETE EXAMPLE

This example classifies messages represented by array references:

    use feature 'case_match';

    for my $value (
        [ "ok", 42 ],
        [ "error", "disk full" ],
        [ "other", 0 ],
    ) {
        case ($value) {
            match ([ "ok", $number ]) {
                say "received $number";
            }
            match ([ "error", $message ]) {
                warn $message;
            }
            match (_) {
                say "unrecognised value";
            }
        }
    }

=head1 WHAT WORKS NOW

The current implementation supports scalar data shapes, bindings and pins,
wildcards, zero-argument value calls, numeric criteria, regular-expression
shapes, nested array and hash references, open composite shapes, array tail
bindings, class-qualified object shapes, guards, explicit subject conversion,
and localized match variables.  Constant-only cases without guards also have
optimized dispatch paths.  The selected dispatch strategy is an implementation
detail; source order still determines which matching clause wins.

Unsupported or ambiguous data-shape syntax is rejected.  It is never silently
ignored, treated as a non-match, or reinterpreted as ordinary code.

=head1 WHAT IS LEFT TO DO

The following remain future design or implementation work:

=over

=item *

Alternatives, optional fields, ranges, and other richer data-shape forms.

=item *

An inheritance or role test for class-qualified shapes.

=item *

A user-defined data-shape protocol.

=item *

Additional binding forms and further dispatch optimizations.

=item *

Removal or expansion of the current final-slurp minimum range.

=item *

Using regular expressions as fragments of larger string shapes, and other
forms of dynamic regex construction.

=back

These are future design and implementation work, not promises about the final
feature.  Because the feature is experimental, its syntax and behavior may
change before release.
