=encoding utf8

=head1 NAME

perlcasematch - a gentle introduction to experimental case and data-shape
matching

=head1 DESCRIPTION

This document introduces the experimental C<case_match> feature.  It assumes
that you know a little Perl, but it does not assume that you have used
data-shape matching before.

Data-shape matching asks two questions at once: does a value have the shape we
want, and which parts of it should receive names?  In more technical terms it
combines structural matching with destructuring.  Many languages call this
"pattern matching".  Here we use C<data-shape matching> to distinguish it
from regular-expression matching.

Enable the feature with:

    use feature qw(case_match say);

The feature is experimental, so its syntax and behavior may change.

=head1 THE BASIC IDEA

A C<case> examines one subject and tries its C<match> clauses from top to
bottom.  The first matching clause runs.  Clauses do not fall through.
The outer case body contains only C<match> clauses.  Each clause's attached
block may contain statements, loops, and nested cases.

    use feature qw(case_match say);

    for my $value (1, 2, 3) {
        case ($value) {
            match (1) { say "one" }
            match (2) { say "two" }
            match (_) { say "something else" }
        }
    }

This prints:

    one
    two
    something else

The later examples assume these features are enabled.  Examples beginning
with C<match> are clause fragments to place inside a C<case>.

The underscore is a wildcard.  It matches any value and does not create a
binding, so it is useful as a final default clause.

If no clause matches, C<case> returns C<undef> in scalar context and an empty
list in list context.  Otherwise, it returns the value of the last evaluated
expression in the selected clause:

    my $description = do {
        case (2) {
            match (1) { "one" }
            match (2) { "two" }
            match (_) { "something else" }
        }
    };
    say $description;       # two

Use C<do { ... }> when using a case result in an assignment.

The leading part inside C<match (...)> is a data-shape description.  It uses
familiar punctuation, but it is not an ordinary expression and is not evaluated
to produce a temporary value.  The optional part after C<if> is different: it
is an ordinary expression used as a guard.

=head1 BINDINGS, PINS, AND GUARDS

A scalar name in a data-shape description gives a matched value a name.
This is called a binding.  The variable is local to that clause, and you do
not write a separate C<my> declaration for it:

    case ($person) {
        match ({ name => $name, age => $age } if $age < 18) {
            say "$name is a minor";
        }
        match ({ name => $name, salary => $salary, ... }) {
            say "$name earns $salary";
        }
    }

Once the complete shape matches, its bindings are available to the guard.
If the guard succeeds, the attached block runs with those bindings.  If the
shape or guard fails, the clause's bindings are discarded and the next
clause is tried.

Bindings have the usual lexical lifetime.  A closure or reference can keep a
bound variable alive after the clause ends, just as it can keep a variable
declared with C<my> alive.  This also applies if a guard stores a closure
elsewhere before returning false or throwing an exception.

An unpinned name is a new binding even if an outer scope has a variable with
the same spelling.  A name listed by C<with>, or prefixed with C<^> in the
data shape, is the exception: it refers to an existing scalar and is checked
instead of filled in.

    my $name = "outside";
    case ("Ada") {
        match ($name) { say $name }   # Ada: a new local variable
    }
    say $name;                       # outside: unchanged

=head2 Naming and pinning

The subject can be given a case-local name with C<as>:

    case (read_record() as $record) {
        match ({ type => "ok", ... }) { use_record($record) }
    }

The subject is evaluated once.  C<as $record> declares a new lexical scalar
containing that value, available throughout the case.  It does not assign to
an outer variable with the same name.

A C<with> clause pins existing values.  Each item may be a variable or an
expression followed by C<as> and a scalar name:

    case ($record)
    with (expected_type() as $wanted, $wanted_version) {
        match ({ type => $wanted, version => $wanted_version, ... }) {
            use_record($record);
        }
    }

The C<as> syntax in a case subject or C<with> clause belongs to this feature.
It is distinct from the similarly named syntax in the namespace feature, and
does not require the C<namespaces> feature.

An existing scalar can also be pinned directly with C<^$name>:

    my $wanted = "ok";
    case ($record) {
        match ({ type => ^$wanted, ... }) { use_record($record) }
    }

The value is snapshotted when the surrounding case begins, so all clauses see
the same pinned value even if a guard or clause body later changes the scalar.
Only an existing scalar lexical may follow the caret.  Outside a data-shape
description, the caret keeps its ordinary meaning.

=head2 Guards

A guard is an ordinary expression checked after the structural match:

    case ($value) {
        match ([ $number ] if $number > 0) {
            say "positive: $number";
        }
        match (_) { say "not a positive one-element array" }
    }

Guards are unrestricted expressions.  They may have side effects or throw an
exception.  A false guard discards that clause's tentative bindings and allows
the next clause to be tried.  An exception is propagated normally, with the
tentative bindings discarded.

For an open-array search, the guard tests the first structurally matching
subsequence. If it is false, matching moves to the next clause; it does not
search for another subsequence within the same clause. Concatenated string
shapes likewise do not retry longer captures when a guard fails.

=head2 Checking constraints before collecting captures

A clause checks its requirements before collecting values that are only
being captured. For example:

    case ([10, 20, 42]) {
        match ([..., $previous, 42, ...]) { say $previous }
    }

The matcher looks for C<42> with a preceding element, then captures that
element. This prints C<20>. It does not fetch a candidate's preceding element
just to discard it when the C<42> requirement fails.

At each array or hash level, literal requirements precede other nested
requirements and tests. Requirements within the same group retain source
order. Reading the enclosing structure comes first, because the matcher
needs to know what it can inspect. Capture-only reads wait until structural
matching succeeds, even when they are nested inside other structures.

Some captures also impose requirements. C<Int($x)> checks a type, and
C<[$x, $x]> compares two values. These need observations during matching.
Regex and concatenation captures also retain results of their checks.
Those observations are reused rather than repeating the checks when
bindings are placed in the clause's lexical variables.

This order applies to tied values, overloaded operations and pattern calls
too. Do not assume that such callbacks run from left to right as written
in the shape. A failed literal requirement can prevent a call from running.
User code in the guard and clause block retains its normal behavior.

Values retained during checking stay alive, but are not frozen: a callback
that overwrites the same scalar can change its value before publication.
Capture-only reads see the contents present when they run. Array searches
keep their initial candidate range, so appending elements in a callback
does not extend the search. Later reads see current contents; missing array
slots behave as C<undef>, and missing hash keys remain absent. The matcher
does not repeat earlier successful checks after a callback changes data.

=head1 SCALAR DATA SHAPES

=head2 Literal strings and numbers

Literal numbers and literal strings are different data-shape kinds:

    case ($value) {
        match (1)   { say "the number one" }
        match ("1") { say "the string one" }
    }

This distinction makes the intended comparison explicit.

Using a string in an earlier numeric expression does not change its kind
for matching. For example, C<"0007"> remains a string after C<0 + $value>
has read it. The same rule applies inside arrays, hashes, and object shapes.

=head2 Undefined values

An undefined value can be matched directly:

    case ($value) {
        match (undef) { say "no value" }
        match (_)     { say "some value" }
    }

=head2 Boolean values

Boolean matching has two forms with different meanings.  The lower-case
C<true> and C<false> patterns ask whether the subject is a boolean value.  They
do not ask whether the subject merely behaves as true or false.  Thus a string
such as C<"yes"> does not match C<true>, even though it is true in a condition.
The builtins C<true> and C<false> produce boolean values, as do comparisons
such as C<< $age < 18 >>.

    use builtin qw(true false);

    case ($value) {
        match (true)  { say "the value is the boolean true" }
        match (false) { say "the value is the boolean false" }
        match (_)     { say "the value is not a boolean" }
    }

The upper-case C<TRUE> and C<FALSE> patterns ask the usual truth-value
question instead.  C<TRUE> matches any value that would be true in an
C<if> statement, and C<FALSE> matches any value that would be false.  Among
ordinary scalar values, C<undef>, the empty string C<"">, the number C<0>,
and the string C<"0"> are false.  All other ordinary scalar values are true.
Boolean values keep their truth value, and objects with boolean overloads
use their overload behavior.

    case ($value) {
        match (TRUE)  { say "the value is truthy" }
        match (FALSE) { say "the value is falsey" }
    }

For example:

    Subject      true    false    TRUE    FALSE
    true         yes     no       yes     no
    false        no      yes      no      yes
    "yes"        no      no       yes     no
    "0"          no      no       no      yes
    ""           no      no       no      yes
    undef        no      no       no      yes

This distinction is useful when a program must tell the difference between
the boolean value C<false> and some other value that happens to be false.
Use C<match (undef)> when undefined and defined-false values must be
distinguished.

=head2 Computed scalar values

A zero-argument function or method call may supply a value computed by a
subroutine:

    sub current_version { 3 }

    case ($version) {
        match (current_version()) { say "current" }
        match (Version->number()) { say "known version" }
    }

The call is made in scalar context if structural checking reaches it.
An earlier failed requirement can skip the call. An open-array search may
call it again for another candidate; it is not cached across candidates.
Calls with arguments are rejected because the left side of C<match> is not
general expression syntax. Use a guard for ordinary computation or a value that
needs arguments.

=head2 Value-kind criteria

These criteria describe the kind of the subject rather than its contents:

=over

=item C<DefinedVal()>

Matches any defined value, so anything but C<undef>.

=item C<ScalarVal()>

Matches any non-reference scalar, including C<undef>, numbers, and strings.

=item C<RefVal()>

Matches any reference, including an unblessed array or hash reference and a
blessed object.

=item C<ObjectVal()>

Matches a blessed reference.  It is narrower than C<RefVal()>: an unblessed
reference matches C<RefVal()> but not C<ObjectVal()>.

=back

Inside a data-shape description these names are criteria, not ordinary calls.
Outside a data-shape description they retain ordinary subroutine semantics,
so a program may define or call a subroutine with one of these names.

Each criterion may take one scalar target.  The target is bound after the type
check succeeds:

    case ($value) {
        match (ObjectVal($object)) { use_object($object) }
        match (RefVal($reference)) { use_reference($reference) }
        match (ScalarVal($scalar)) { use_scalar($scalar) }
    }

Put the more specific criterion first.  Every object is also a reference,
so putting C<RefVal()> first would prevent the object clause from running.

The target is a clause-local binding and cannot also be pinned by C<with>.
Using a criterion without an argument performs only the type check.

Repeating a scalar binding requires the values to agree. References agree
only when they refer to the same thing, not merely when they print the same
way. This applies both to C<[$item, $item]> and to typed bindings such as
C<[RefVal($item), RefVal($item)]>.

Two undefined values also agree, but an undefined value never agrees with
a defined value, including the empty string. Other non-reference values
are compared as strings. These rules also apply when comparing a value
with a pinned scalar.

=head2 Numeric value criteria

Numeric criteria distinguish native numeric values from numeric-looking
strings:

=over

=item C<Int()>

Matches a native integer value.  It does not match a string regardless of its
contents.

=item C<Float()>

Matches a native floating-point value.  It does not match a string regardless
of its contents.

=item C<Num()>

Matches a native integer or floating-point value.  A string is not converted
just to make it fit this criterion.

=item C<IntStr()>

Matches an integer value or a string containing an integer.  Surrounding
whitespace and leading-zero padding are accepted unless wrapped by C<Strict()>.

=item C<FloatStr()>

Matches a floating-point value or a string containing a floating-point number,
including exponent notation.  Surrounding whitespace and leading-zero
padding are accepted unless wrapped by C<Strict()>.

=item C<NumStr()>

Matches anything accepted by C<IntStr()> or C<FloatStr()>.

=item C<NumEq(CONSTANT)>

Compares the subject with the literal constant using numeric C<==> semantics.
It is matching-only and cannot bind a value.

=back

The string-bearing criteria will bind the original value.  Matching C<"0007">
does not turn the binding into C<7>:

    case ($value) {
        match (IntStr($integer_text)) { use_integer($integer_text) }
        match (FloatStr($float_text)) { use_float($float_text) }
    }

=head3 Checking numeric spelling with Strict

C<Strict(...)> may wrap C<IntStr()>, C<FloatStr()>, or C<NumStr()> to reject
surrounding whitespace and leading-zero padding.  For example,
C<Strict(IntStr())> accepts C<"7"> but rejects C<"0007"> and C<" 7 ">.
C<Strict(FloatStr())> accepts C<"0.0"> but rejects C<"0000.0">.
Successful bindings still receive the original value.

=head3 Numeric equality with NumEq

C<NumEq(CONSTANT)> uses the usual numeric-conversion rules.  For example,
C<NumEq(0)> matches C<"0000">, C<"0.0">, and C<"0000.0">.  It also matches
C<"A"> as zero and emits the usual numeric warning when warnings are enabled.
A non-literal argument or a destructuring target is not allowed.

C<Strict(NumEq(CONSTANT))> adds a different check: a string must begin with
numeric data before the numeric comparison is attempted.  For example,
C<Strict(NumEq(1))> accepts C<"+1"> and rejects C<"+A"> without a numeric
warning.  This form does not require canonical spelling: C<"0001"> can
still match.  A numeric prefix followed by nonnumeric text can still cause
the ordinary comparison warning.

C<Strict()> is not accepted around C<Int()>, C<Float()>, or C<Num()>.

=head1 REFERENCE AND OBJECT SHAPES

A backslash describes a scalar reference shape:

    my $number = 42;
    my $reference = \$number;

    case ($reference) {
        match (\$value) { say "the value is $value" }
    }

C<\\$value> describes one additional scalar-reference layer.  A reference
shape is structural; it does not evaluate the description as a reference
constructor.

C<RefVal($name)> is different from C<\$name>.  The former checks any reference
and binds the outer reference itself.  The latter checks a scalar reference
and binds the value reached through it.  Array and hash shapes can be nested in
the same way.

=head2 Arrays

An array shape matches an array reference.  Without an ellipsis, it must have
exactly the listed number of elements:

    match ([ $x, $y ]) { say "point: $x, $y" }

With no elements listed, C<match ([])> matches only an empty array
reference. It does not match an empty hash reference or C<undef>.

For arrays, C<...> may appear at the beginning, at the end, or at both ends:

    match ([ $first, ... ])
    match ([ ..., $last ])
    match ([ ..., "start", $middle, "end", ... ])

The last form searches from the left and binds the first matching subsequence.
For example:

    case ([ "skip", "start", 10, "end", "start", 20, "end" ]) {
        match ([ ..., "start", $middle, "end", ... ]) {
            say $middle;     # 10, from the first matching subsequence
        }
    }

The elements between the ellipses must be consecutive.  The ellipses allow
elements before and after that group; they do not allow gaps within it.

An array slot that has never been assigned is treated as C<undef>. Matching
does not fill these holes in the original array. A tail binding includes
the undefined values, preserving their positions in the captured tail.

=head2 Hashes

C<match ({})> matches an empty hash reference. Even a single key whose
value is C<undef> makes that hash nonempty. Empty array and hash shapes
also work inside larger shapes, such as C<[[], {}]>, and with a class
name, such as C<Point {}> for a C<Point> object with no fields.

A hash shape lists keys that must be present.  Without an ellipsis, the hash
must have exactly those keys.  A trailing C<...> permits extra keys:

    case ({ status => "ok", value => 42, source => "cache" }) {
        match ({ status => "ok", value => $value }) {
            say "exact record";
        }
        match ({ status => "ok", value => $value, ... }) {
            say "record with extra keys: $value";
        }
    }

This prints C<record with extra keys: 42>.  The first clause fails because
the subject also has a C<source> key.  Removing that key makes the first
clause match instead.

A present key whose value is C<undef> is different from a missing key.
For a tied hash, the shape checks C<EXISTS> before reading the value with
C<FETCH>; a missing key does not match even if C<FETCH> would return undef.
With a wildcard value, as in C<{ name => _, ... }>, only the key's presence
is required. Its value is not fetched.

Repeating a constant key in the same hash shape is a compile-time error.
For example, C<{ x => 1, x => 1 }> is not a valid shape.  Separate nested
hash shapes may each use the same key.

A key supplied by a pinned variable or a zero-argument call is determined
at runtime.  If two such keys turn out to be equal, both value requirements
must hold for that one key.  This is not an error, but it does not permit
extra keys: a shape that covers only C<x> cannot match C<{ x => 1, y => 2 }>
without an ellipsis.

Array and hash shapes may be nested:

    match ({ point => [ $x, $y ], ... }) { say "point: $x, $y" }

Every hash entry must have both a key and a value shape. An unpinned name
cannot capture a key: use a literal key, a pinned scalar, or a supported
zero-argument call to say which key to inspect.

=head2 Array tail bindings

An array shape can capture its remaining tail with an array binding.  The
binding may contain zero or more elements:

    match ([ 1, 2, @rest ]) { say "the rest is @rest" }

The binding must be the final pattern element.  C<@rest:N> requires at least
C<N> remaining elements while capturing the complete tail:

    match ([ 1, 2, @rest:3 ]) { say "three or more: @rest" }

C<N> is a nonnegative integer from C<0> through C<2**32 - 1>, written as
decimal digits.  Larger minima are compile-time errors.  If fewer than
C<N> elements remain, the clause does not match. For example,
C<[1, 2, 3, 4]> has only two elements after C<1> and
C<2>, so it does not match C<[1, 2, @rest:3]>.

A tail binding, also called a slurp, cannot be combined with an ellipsis or
another slurp.

The tail contains copies of the element values, not aliases to the source
slots. Assigning to C<$rest[0]> does not change the source element, and
assigning to the source element does not change C<$rest[0]>. References
still point to the same objects or aggregates; this is not a deep copy.
For example, changing a field through a captured reference changes the
same object that the source refers to.

=head2 Class-qualified shapes

A blessed reference can be matched by putting its class name before an array,
hash, or reference shape:

    my $point = bless { 'x' => 3, 'y' => 4 }, 'Point';

    case ($point) {
        match (Point { 'x' => $x, 'y' => $y }) {
            say "point: $x,$y";
        }
    }

Hash shapes inspect quoted fields, array shapes inspect positional values,
and scalar-reference shapes can bind their referents.  For an object created
with C<class>, use the field names including their sigils:

    use feature 'class';

    class Position {
        field $x :param;
        field $y :param;
    }

    case (Position->new(x => 3, y => 4)) {
        match (Position { '$x' => $x, '$y' => $y }) {
            say "position: $x, $y";
        }
    }

This prints C<position: 3, 4>.  The quoted C<'$x'> and C<'$y'> identify
the fields, including their sigils.  The unquoted C<$x> and C<$y> are new
clause-local variables that receive those fields' values.  They are also
available in a guard and do not overwrite outer variables with the same names.

The class name must match exactly in this version; inheritance and role
matching are not used.
Missing fields do not match.  These shapes inspect the object directly and do
not call constructors, accessors, or arbitrary methods.  Tied and magical
nested values use normal read semantics, and overload is used when the
selected shape requires string, numeric, or boolean conversion.  Captured
references retain their identity.

The matcher uses the fetched value for both a nested type check and its
binding; publishing that binding does not fetch the tied source again.
If your guard or clause body reads the tied source itself, that is a
separate ordinary read and may return a different value.

=head1 REGULAR-EXPRESSION SHAPES

A regular expression can be used as a data shape:

    case ($text) {
        match (/^user: (\w+)$/) {
            say "user is $1";
        }
        match (/^person: (?<person>\w+)$/) {
            say "person is $person";
        }
    }

Numbered captures and the usual named-capture variables remain available in
the clause.  A named capture also creates a clause-local scalar binding.  If
a named group does not participate in a successful match, its binding is
C<undef>.

A shape may contain several regular expressions, including inside arrays,
hashes, and class-qualified shapes.  Each expression supplies its own named
bindings:

    case (["Ada", "42"]) {
        match ([ /^(?<name>\w+)$/, /^(?<id>\d+)$/ ]) {
            say "$name has id $id";
        }
    }

The ordinary capture variables, such as C<$1> and C<%+>, describe the most
recent successful regex match; they are not combined across expressions.

Named clause bindings are copies of the captured text. Use these lexical
variables when you need to keep the text across further matching or recursive
calls. The ordinary capture variables still follow the regex engine's rules;
they are not independent copies belonging to each clause invocation.

Give captures in separate regexes different names if you want to use all
their values.  If several regexes in one clause use the same capture name,
the compiler issues a C<syntax> warning. Only the first regex in source order
supplies the clause-local variable; later captures with that name are not
visible through it, even if constraint scheduling executes a later regex first.
This also applies when the first regex's named group did not participate:
the variable stays C<undef>, even if a later regex captures a value.

Repeated names I<within a single regex> work as usual, without this warning.
For example, C</(?E<lt>numE<gt>one)|(?E<lt>numE<gt>two)/> binds C<$num> to
C<"two"> when matching C<"two">.  The regex engine chooses the first
participating capture with that name, just as it does for C<$+{num}>.

The clause can use the captures from its successful match.  When the case
ends, the previous values of C<$1>, C<$2>, C<%+>, C<%->, and the other regex
match variables are restored.

Static regular expressions are compiled once and reused when a shape tests
multiple candidates, such as during an open-array search.  Dynamic expressions,
including interpolated expressions such as C</thing-$re-thing/>, are rejected
in a data-shape position.  Regex code blocks such as C<(?{ ... })> and
C<(??{ ... })> are also rejected.  Use a guard for these forms:

    match (_ if $subject =~ /thing-$re-thing/) { ... }

A regular expression cannot currently be used as a fragment of a larger
concatenated string shape.  Unicode and byte behavior remains the
responsibility of the regular-expression engine.

=head1 CONCATENATED STRING SHAPES

A string shape can combine literal text with unpinned scalar names.  Each
name receives the part of the subject between the surrounding literal or
pinned fragments:

    case ($text) {
        match ("x_" . $middle . "_z") {
            say "middle is $middle";
        }
    }

This matches C<x_middle_z> and binds C<$middle> to C<middle>.  Multiple
captures are allowed when literal or pinned text separates them:

    match ("a" . $first . "b" . $second . "c") {
        say "first=$first second=$second";
    }

Matching proceeds from left to right.  Each capture uses the shortest value
that reaches the next literal or pinned fragment.  Prefix-only and suffix-only
forms such as C<"x" . $suffix> and C<$prefix . "z"> are supported.  Empty
captures are allowed.

Each unpinned capture name may occur only once in a concatenation.  Adjacent
unpinned captures, repeated capture names, and fragments separated only by an
empty literal are rejected because they do not provide an unambiguous
boundary.

Concatenation is the only structural expression currently supported.  Calls
with arguments, arithmetic, and other unsupported expressions will throw an
exception.  Literal strings and values with usable overloaded stringification
follow normal string and Unicode/byte behavior.  Concatenation does not apply
to numeric values.  Use C<ToString()> on the subject to convert a number to
a string before matching.

=head1 EXPLICIT SUBJECT CONVERSION

The grammar provides three explicit subject conversions:

    case (ToInteger $value) { ... }
    case (ToFloat   $value) { ... }
    case (ToString  $value) { ... }

The subject is evaluated once and converted before any clause is tested.
These subject conversions let you choose how strings and numbers should be
treated:

    case (ToInteger "12") {
        match (12) { say "integer twelve" }
    }
    case (ToFloat "2.5") {
        match (2.5) { say "floating-point two and a half" }
    }
    case (ToString 12) {
        match ("12") { say "string twelve" }
    }

An undefined value remains undefined, and references pass through unchanged:

    case (ToString undef) {
        match (undef) { say "still undefined" }
    }
    case (ToInteger [3, 4]) {
        match ([ $x, $y ]) { say "still an array: $x, $y" }
    }

=head1 A COMPLETE EXAMPLE

This shorter version of the demonstration in F<t/comp/case_match_examples.t>
classifies a mixture of strings, arrays, and hashes.  It combines extraction,
pinning, and a guard in one case:

    use feature qw(case_match say);

    my $wanted_status = "ok";

    for my $value (
        "prefix_middle_suffix",
        [ "point", 3, 4 ],
        [ { name => "Ada" }, { name => "Lin" } ],
        { status => "ok", code => 200, source => "cache" },
        { status => "ok", code => 500 },
        "something else",
    ) {
        case ($value) {
            match ("prefix_" . $inner . "_suffix") {
                say "inside <$inner>";
            }
            match ([ "point", $x, $y ]) {
                say "point ($x,$y)";
            }
            match ([ { name => $first }, { name => $second } ]) {
                say "names: $first and $second";
            }
            match ({ status => ^$wanted_status, code => $code, ... }
                   if $code < 400) {
                say "accepted status: $code";
            }
            match ({ status => $status, ... }) {
                say "other status: $status";
            }
            match (_) {
                say "unrecognised value";
            }
        }
    }

This prints:

    inside <middle>
    point (3,4)
    names: Ada and Lin
    accepted status: 200
    other status: ok
    unrecognised value

The record with code C<500> passes the pinned status check, but its guard
fails.  Matching continues with the broader status clause.  Putting that
broader clause first would prevent the guarded clause from being reached.

The demonstration test in the source tree includes more combinations,
including open-array searches, array tails, regex captures, and references,
and checks the expected results.
